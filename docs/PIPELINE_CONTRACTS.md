# Контракты пайплайна: что оркестратор зовёт у ваших сервисов

Оркестратор (`go-ingest`, задача G1-14) сам двигает новости и сюжеты по статусам
и по очереди зовёт ваши сервисы. **Чтобы конвейер дошёл до вашего этапа, нужно
реализовать ровно один эндпоинт** — ниже какой, с каким телом и что делать с базой.

```
новость  RAW ─▶ DEDUPED ─▶ ENRICHED ──────▶ (склейка в сюжет)
                    │          ▲    py-ml /v1/enrich        │
                    ▼          │    или fallback в Go        ▼
                FILTERED ◀─────┘                      сюжет ENRICHED
                (шум)                                       │  go-api  /internal/v1/stories/{id}/score
                                                            ▼
                                                      сюжет SCORED
                                                            │  java-agent /v1/insights (на каждую компанию)
                                                            ▼
                                       сюжет ANALYZED  или  FILTERED (не релевантен никому)
```

## Общие правила для всех трёх

- **501 или 404 = «ещё не готово».** Оркестратор пропустит этап до следующего тика
  (раз в 10 с) и **не потратит попытки** записей. Сейчас ваши заглушки отвечают 501 —
  поэтому конвейер аккуратно стоит перед вашим этапом и ничего не ломает.
  Недоступный сервис (не поднят, не резолвится) — то же самое.
- **Любой другой не-2xx или таймаут — сбой записи.** Она уходит в ретраи с
  экспоненциальным бэкоффом (30 с, 1 мин, 2 мин…, не дольше 30 мин), после
  5 попыток — в `dead_letters` и статус FAILED. Текст ошибки виден в `job_attempts.last_error`.
- **Будьте идемпотентны.** После сбоя оркестратор повторит вызов целиком — тот же
  запрос может прийти дважды.
- **Ключа к моделям у вас нет и не нужно.** Все вызовы моделей — через
  `POST http://llm-gateway:8091/v1/complete` ([gateway.yaml](../api/openapi/gateway.yaml)).

## Python: `POST http://py-ml:8000/v1/enrich`

Включается переменной `USE_ML_FALLBACK=false` в `go-ingest`. Пока она `true`
(по умолчанию), вместо вас работает словарный fallback внутри Go — так что
конвейер не ждёт питониста, а питонист может спокойно доводить модель.

**Запрос:**

```json
{ "news_id": "6f1c…", "title": "Экспорт стали в Китай вырос", "body": "Полный текст новости…" }
```

**Ответ 200:**

```json
{
  "embedding": [0.012, -0.034, …],
  "entities": [
    { "type": "COUNTRY",   "value": "КИТАЙ",      "mentions": 2 },
    { "type": "COMMODITY", "value": "сталь",      "mentions": 3 },
    { "type": "RISK_TAG",  "value": "export",     "mentions": 1 }
  ],
  "okved_hints": [ { "code": "24", "label": "Металлургия", "weight": 1.0 } ],
  "noise_score": 0.08,
  "model_version": "pyml-v1"
}
```

- `embedding` — **768 чисел** (размерность колонки `vector(768)`), или `null`, если эмбеддинга нет.
- `entities[].type` — `COUNTRY` | `COMMODITY` | `RISK_TAG`. Страны — **в написании ФТС
  из данных** (`КИТАЙ`, `ТУРЦИЯ`, `ОАЭ`…), чтобы Go #2 сравнивал с `FTS_COUNTRY_NAME`
  простым равенством. Риск-теги — те же, что у продуктов КИБ в плане Java:
  `rate_risk`, `fx_risk`, `trade_restriction`, `supply_chain`, `export`, `import`,
  `inflation`, `liquidity_gap`, `capex`.
- `okved_hints[].code` — группа ОКВЭД (`24`, `46`, `68`…), `weight` — 0..1.
- `noise_score` — 0..1. **Не ниже 0.8 → новость отсеивается** и дальше не идёт
  (`INGEST_ORCH_NOISE_THRESHOLD`).
- `model_version` — обязательно: по нему видно, какой версией сделано обогащение.

**В базу вы не пишете.** Ответ сохраняет оркестратор в `news_enrichment` — у перехода
`DEDUPED → ENRICHED` один владелец. Посмотреть, как это выглядит на fallback:

```sql
SELECT n.title, e.noise_score, e.okved_hints, e.entities, e.model_version
FROM news_enrichment e JOIN news n ON n.id = e.news_id
ORDER BY e.created_at DESC LIMIT 20;
```

Склейку в сюжеты (`P-04`) сейчас тоже делает fallback — по сходству заголовков,
строго (5 сюжетов из 270 на Д2, ложных склеек ноль, но и перепечатки с другим
заголовком не ловит). Семантическую склейку подключим отдельным эндпоинтом,
когда будет готова, — договоримся о контракте.

## Go #2: `POST http://go-api:8090/internal/v1/stories/{story_id}/score`

**Запрос:** тело пустое (`{}`), всё нужное — в базе по `story_id`:
`stories`, `story_news` → `news` → `news_enrichment` (отрасли, страны, сырьё, риск-теги).

**Что сделать:** подобрать компании по признакам и **записать в `story_company_scores`**
(это ваша таблица): `story_id`, `company_id`, `relevance_score` 0..1, `match_reasons`
(JSON — человекочитаемые причины, это блок «Почему это про вас»), `model_version`.

**Ответ 200:**

```json
{ "companies": 3 }
```

Сколько компаний нашлось — для live-панели. Ноль — нормальный ответ: сюжет просто
никому не релевантен, оркестратор отсеет его на следующем шаге без вызова агента.

**Что дальше делает оркестратор:** берёт из `story_company_scores` компании с
`relevance_score ≥ 0.5`, самые релевантные первыми, **не больше 3 на сюжет** — и только
их отдаёт агенту (`INGEST_ORCH_RELEVANCE_THRESHOLD`, `INGEST_ORCH_MAX_COMPANIES_PER_STORY`).
Это главная экономия токенов: порог и лимит — ваш рычаг качества и наш рычаг бюджета.

Сейчас на этом шаге стоят **270 сюжетов** — они пойдут дальше, как только появится эндпоинт.

## Java: `POST http://java-agent:8081/v1/insights`

Вызывается **на каждую пару** «сюжет — компания», прошедшую порог.

**Запрос:**

```json
{ "story_id": "a1b2…", "company_id": "U_67" }
```

**Что сделать:** построить разбор (PLAN → инструменты → DRAFT → CRITIC → ADAPT → EMIT)
и записать сами `insights`, `evidence`, `agent_runs`. Позицию банка брать из
`research_chunks` — там уже **123 чанка из 9 материалов ЦМИ с номерами страниц**
([data/README.md](../data/README.md)).

**Ответ 201 (или 200, если такой разбор уже есть):**

```json
{ "insight_id": "c3d4…" }
```

- **Идемпотентность обязательна:** в `insights` уникальный ключ
  `(story_id, company_id, model_version)`. Если разбор для пары уже построен —
  верните его `insight_id` с 200, не стройте заново и не тратьте токены.
- Таймаут на вызов — **180 с** (`INGEST_AGENT_TIMEOUT`). Агент дольше — оркестратор
  считает это сбоем и повторит позже.
- Если одна из компаний сюжета упала, оркестратор повторит **все** пары сюжета —
  поэтому идемпотентность здесь не формальность.

Когда все пары сюжета разобраны, сюжет становится ANALYZED.

## Как посмотреть, где сейчас конвейер

```sql
-- новости по статусам
SELECT s.code, count(*) FROM news n JOIN pipeline_statuses s ON s.id = n.status_id GROUP BY 1;
-- сюжеты по статусам
SELECT s.code, count(*) FROM stories st JOIN pipeline_statuses s ON s.id = st.status_id GROUP BY 1;
-- что ретраится и почему
SELECT entity_kind, stage, attempts, next_run_at, last_error FROM job_attempts ORDER BY updated_at DESC;
```

Или вживую — SSE-стрим всех переходов:

```bash
curl -N localhost:8080/v1/pipeline/stream
```
