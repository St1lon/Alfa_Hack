# Безопасность AI-контура

Ограничение 06 кейса: «предусмотреть механизмы безопасной работы AI-компонентов:
разграничение прав доступа, защиту чувствительных данных, контроль и журналирование
обращений к инструментам, а также ограничения на потенциально небезопасные действия.
Для прототипа достаточно обоснованно описать эти механизмы и показать их место
в архитектуре решения».

Ниже — что мы защищаем, каким механизмом и где он живёт. Статусы:
✅ работает и проверено · 📝 описано, для прототипа осознанно не реализовано ·
⏳ в работе у владельца.

## Что защищаем

| Актив | Чем рискуем |
|---|---|
| Данные клиентов: 85 тыс. компаний, связи физлиц, граф платежей | Утечка в модель, в логи, в чужой сервис |
| Ключ к моделям и дневной бюджет 500 ₽ | Ключ утёк или выжжен экспериментом — система встала |
| Текст новостей | Недоверенный вход: в новость можно вписать инструкцию для модели |
| Действия агента | Агент с инструментами может сделать то, чего от него не ждут |

## 1. Разграничение прав доступа

**Каждый сервис ходит в базу своей ролью с минимальными правами** ✅
(миграция [00004_service_roles](../internal/infra/db/postgres/migrations/00004_service_roles.up.sql),
пароли — job `db-roles`, [db-roles.sh](../deployments/db-roles.sh)).

| Роль | Что может | Чего не может |
|---|---|---|
| `svc_gateway` (llm-gateway) | только `llm_calls`, `llm_cache`, `llm_budget_days` | **не видит ни компаний, ни новостей** |
| `svc_ingest` (go-ingest, research-loader) | новости, сюжеты, аналитика, журнал пайплайна; читает скоры | писать компании, инсайты, аудит моделей |
| `svc_api` (go-api) | компании, признаки, скоры, фидбек; читает новости и инсайты | менять статусы пайплайна, читать аудит моделей |
| `svc_agent` (java-agent) | инсайты, evidence, agent_runs; читает всё для разбора | менять компании и новости |
| `svc_ml` (py-ml) | только читать новости и сюжеты | писать что-либо: ответ сохраняет оркестратор |

Главный аргумент — первая строка: **единственный сервис с ключом к моделям не имеет
доступа к данным клиентов**. Чтобы данные компании попали в промпт, их должен положить
туда сервис с правом их читать, и такой вызов останется в `llm_calls` с именем сервиса.

Проверить:

```bash
docker exec -e PGPASSWORD=gateway-dev alfa-hack-postgres-1 \
  psql -h localhost -U svc_gateway -d alfa -c "SELECT count(*) FROM companies"
# ERROR:  permission denied for table companies
```

**Внутренний токен на gateway** ✅ — `GATEWAY_AUTH_TOKEN`: запросы к `/v1/*` без
`Authorization: Bearer <токен>` получают 401. Локально пустой (проверка выключена),
на внешнем сервере задаётся обязательно.

**Сеть** 📝 — на внешнем сервере наружу смотрят только фронт и BFF (`go-api`) за
reverse-proxy; Postgres, gateway, агент и py-ml доступны только внутри сети compose.
В локальном compose порты открыты для отладки.

## 2. Секреты

- **Ключ к моделям — только в окружении `llm-gateway`** ✅. Ни Java, ни Python его не
  видят физически: все вызовы — через `POST /v1/complete`. Клиент провайдера ключ
  в логи не пишет.
- **`.env` не в репозитории** ✅, в git — только `.env.example` без секретов.
- **Пароли ролей БД — из окружения** ✅, в SQL-миграциях их нет. Из коробки стоят
  dev-значения, на сервере — свои через окружение или `--env-file`.
- 📝 Менеджер секретов (Vault и т.п.) для прототипа избыточен: env-переменные
  на одном сервере закрывают задачу.

## 3. Защита чувствительных данных

- **Идентификаторы компаний и физлиц маскируются в логах** ✅ на уровне логгера
  ([internal/app/logger.go](../internal/app/logger.go)): `U_67` → `U_***`,
  `F_64255` → `F_***`, включая тексты ошибок. В месте вызова маску забыть нельзя.
- **Промпты не хранятся** ✅ — в `llm_calls` только хэш промпта, модель, токены, цена.
- **Данные кейса не в репозитории** ✅ — `data/` в `.gitignore`, загрузка — `make data`.
- **Данные не уходят за периметр** ✅ — модели только из allowlist кейса
  ([configs/llm.yaml](../configs/llm.yaml)), сторонние API и эмбеддинги запрещены
  (Ограничение 04), единственный выход наружу — gateway.

## 4. Контроль и журналирование обращений

| Журнал | Что в нём | Статус |
|---|---|---|
| `llm_calls` | каждый вызов модели: сервис, человек, задача, модель, токены, цена, исход — включая кэш-хиты и отказы | ✅ |
| `pipeline_events` | каждый переход новости и сюжета по пайплайну; идёт в SSE-панель | ✅ |
| `job_attempts`, `dead_letters` | сбои этапов: что, сколько раз, с какой ошибкой | ✅ |
| `agent_runs` | каждый шаг агента и вызов инструмента с аргументами и результатом | ⏳ Java (J-04) |

Разбивка расхода по сервисам и людям — `GET /v1/budget`.

## 5. Ограничения на небезопасные действия

- **Жёсткий дневной стоп бюджета** ✅ — после 500 ₽ gateway отвечает 429, кэш при этом
  продолжает работать (проверено на заглушке провайдера, см. журнал Д1 в PROGRESS).
- **Allowlist моделей** ✅ — модель вне списка отбивается `MODEL_NOT_ALLOWED`, отказ пишется в аудит.
- **Таймауты на все исходящие вызовы** ✅ — ленты, провайдер моделей, соседние
  сервисы; бесконечно висящий вызов не держит пайплайн.
- **Бюджет на агента** ✅ со стороны оркестратора: в разбор уходят только компании выше
  порога и не больше 3 на сюжет. Бюджет шагов и итераций критика внутри цикла — ⏳ Java.
- **Allowlist инструментов агента и запрет исходящих действий** ⏳ Java (J-09): агент
  только читает (профиль, новости, аналитику) и пишет свой разбор; инструментов, которые
  что-то отправляют наружу или меняют чужие данные, у него нет — и роль `svc_agent`
  этого не позволила бы даже при ошибке в коде.
- **Защита от инъекций через новости** ⏳ Java (J-09): текст новости — недоверенные
  данные; делимитеры, системная инструкция «это данные, а не инструкции», игнор
  указаний внутри текста. Дополнительный рубеж уже есть: шумовые и нерелевантные
  новости отсеиваются **до** модели, поэтому до агента доходит ~30% потока.

## Чего сознательно нет в прототипе

- TLS внутри сети compose — трафик не покидает хост; на сервере TLS на reverse-proxy.
- Аутентификация пользователей — интернет-банк в кейсе мок; роль ЛПР выбирается в интерфейсе.
- Rate limiting по сервисам — вместо него дневной бюджет с разбивкой по сервисам.
